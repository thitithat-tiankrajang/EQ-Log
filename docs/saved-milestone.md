# Milestone 9 — explicit Saved retention

## Boundary and source audit

See [saved-drive-source-audit.md](saved-drive-source-audit.md). This milestone adds a new, explicit per-participant Saved relation. It does not migrate or reinterpret old Private Library items, change live moves, change the old private auto-archive path, create folders, or implement Trash/Overflow. The old private quota still applies to old room creation and Private Library copies; the History finalizer already keeps completion independent of a private archive quota failure. **The new Saved capacity is never consulted by a game finalizer.**

## Schema and retention

`saved_game_items(source_kind, source_id, participant_id, saved_at)` has a composite FK to the seated participant's permanent `game_history` row. A Host without a seat and a spectator cannot Save. The PK makes retries idempotent. Only the authenticated `save_completed_game` RPC or the trusted legacy validation path writes ownership; browser table grants are absent. Stage references its permanent `stage_completed_attempts.record`. A normal trusted Compact source references `recent_game_payloads.record`, the same immutable bytes used by Recent. A complete, decoder-validated legacy v3 archive is frozen once in `saved_legacy_payloads` per source, never converted or labeled Compact. Another seated participant can reference that same frozen legacy payload. Incomplete v1/v2/partial v3 archives stay on their existing read path and cannot become a full Saved replay.

A History seat alone does not renew expired replay access. A new normal Save requires that participant's own Recent relation, an archive they may already open, or the legacy private archive owned by the *recorded Host of that same seated game*. This prevents a player from reviving an expired Recent replay merely because another player Saved the shared bytes. A seated Hosted player can explicitly Save their own completed game without giving the non-playing Host Saved ownership; the Host-owned archive itself remains private and the player receives only the safe replay projection. An existing Saved owner can still retry and open after all other references and archives disappear.

The `save-completed-game` Edge endpoint authenticates the caller. Compact/Stage Save goes through the authenticated database RPC. A new legacy Save invokes a service-only source reader, reconstructs and safely projects the record, checks its game ID and available History scores, then calls a service-only writer with the database's SHA-256 hash of the exact source JSONB. The writer checks that hash again inside the capacity transaction; source changes cause a retry, not a silently different Saved replay. Direct authenticated calls cannot bypass legacy validation. Raw payloads remain service-only; replay continues through `archive-replay` and the existing safe projection. The owner's Saved candidate is preferred over a mutable old archive of the same game.

The authoritative `private_drive_limit` capability now resolves to Free 100, EQ Plus 1000, EQ Pro 1000. Save acquires the same per-account transaction lock as plan grant/revoke, reads `plan_effective`, counts only `saved_game_items`, and inserts atomically. At capacity, duplicate retries still return the existing row. A downgrade leaves all rows and replay access intact, while new Saves are refused until the active count is below the current limit. No byte quota is used.

For normal Compact, `recent_retain_completed_source`, Save and `cleanup_unreferenced_recent_payload` share a per-source lock. Cleanup can delete a payload only when neither `recent_game_items` nor `saved_game_items` references it; the immutable trigger checks again. Frozen legacy payloads have the same reference check and a separate service-only cleanup operation. A reader obtains ownership and payload in one SQL statement, so eviction and cleanup cannot split that read. Cleanup is service maintenance; Milestone 10 will own scheduling and deletion/trash lifecycle. Stage remains in its permanent terminal table. The Stage Recent check now accepts the sealed game's internal game ID being distinct from the room ID, matching the actual Stage lifecycle.

A source-level trigger serializes payload inserts and rejects a Compact/legacy pair for the same source. A Saved replay therefore cannot silently switch to a later backfill in the other format.

## UI and mode isolation

Me → History shows independent Recent, Saved and `can_save` status, offers Save only for an eligible full Compact or legacy replay, and displays the database's capacity refusal. A Hosted seat with a Host-owned private source is shown "Save to open replay" without a false open link. Me → Saved lists metadata, capacity and replay links; it does not load full records per row. No folders or destructive Unsave action are exposed. Ranked has no eligible safe post-game payload and remains unavailable. Stage result/progression, Ranked rating, normal stats, active boards, bot Credits, Hosted permissions, History permanence, Recent latest-20 ordering and Compact semantics are unchanged.

The remaining Stage authority label is `captured_client_state` in History and `client-reported` in the Compact provenance. Sealed start and terminal capture are server controlled, while intermediate move/scoring state is still client submitted. Saved does not upgrade this to a server-verified competitive win. A full internal payload may contain racks, bag order and other private facts; all browser replay reads still use the established safe projection. Product policy on post-game hidden information remains open.

## Measurements

An isolated PostgreSQL clone of the Saved table and both indexes, with 1,000 rows, measured a mean 72-byte tuple, 81,920 B heap, 221,184 B indexes and 335,872 B total (about 336 B per ownership relation). A real 20-item Saved metadata RPC response was 8,121 raw JSON bytes. A trivial Compact test game was 1,568 raw JSON bytes; it is **not** a representative full match.

The validated legal corpus previously measured 39,991 B for 40 actions, 54,818 B for 60 actions plus finish, and 49,649 B for a 39-action natural finish. A declared 60% / 30% / 10% mix has a **calculated** mean of 45,405 B per distinct payload. At that mix, 100 distinct records are about 4.54 MB raw JSON plus 0.034 MB Saved relation storage; 1,000 are about 45.4 MB raw JSON plus 0.336 MB relation storage. If 20 Recent records are also Saved, shared Compact storage avoids about 0.91 MB of duplicated raw payload in this mix. These are modeled raw JSON totals from measured corpus sizes, not measured PostgreSQL JSONB/TOAST disk cost or a guaranteed per-user bill. Two participants can share a source, reducing physical payload cost further. No cross-user content-hash deduplication was added.

## Validation and remaining boundaries

`saved_completed_games_smoke.sql` covers Free 99→100 and refusal at 101, Plus 999→1000 and refusal at 1001, Pro 1000, duplicate Save, downgrade preservation, expired Recent denial, per-user access, permissions, full-Saved Stage terminal/History/Recent independence, Stage's distinct sealed game ID, mixed-format rejection, retained payload cleanup refusal and orphaned legacy payload cleanup. `saved-games-local.test.ts` exercises the real endpoint and database with duplicate and different-game concurrent Saves, plan grant racing Save, downgrade, Recent eviction racing Save, shared retained payload, safe replay, seated Hosted Save without Host ownership, legacy v3 validation/freezing, retained legacy cleanup refusal, malformed legacy refusal and cross-user isolation. Existing Recent, History, archive, Stage and Ranked tests are run separately. `saved-ui.test.tsx` covers explicit Save, refusal, Hosted eligibility and metadata listing.

Remaining work belongs to Milestone 10 or another track: define old Private Library migration and Trash/Overflow semantics; schedule reference-aware cleanup; decide user-facing removal/restoration; resolve final-rack/clock disclosure policy; add a trusted normal Compact terminal producer for modes currently relying on legacy archives; and design a safe Ranked post-game payload if desired. Games with no durable replay source cannot be Saved. Existing private in-progress rooms and legacy archive behavior remain untouched and readable.
