# Stage terminal authority audit (before implementation)

Base: `840ef0e24a558e4392c3399bd2dd487fadb94a95`, existing `codex/compact-completed-game` worktree. This traces the production Supabase Stage path, not the development-only `survival-playtest` service.

## Actual lifecycle and trust

1. An administrator seals `survival_levels.start_canonical` from the current seeded game builder. The seal has all 100 physical tiles and nonzero scores, turn and side. It is server stored, although its values originated in administrator client code. `create_stage_attempt` checks approval/admin membership, an approved/sealed level, and enabled `authur_strong`; it creates a private Stage `room_live` row (`archive_policy='none'`), one `survival_attempts` row, and an idempotency request in one transaction. Room purpose, bot identity, owner and attempt identity are server frozen.
2. `createStageAttempt` then commits the initial client-built game. `check_stage_commit` compares its canonical physical state and opening score/turn/side to the level seal. A newly created but never initially committed room has an attempt row but no verified initial state.
3. Ordinary moves use `commit_live_game_command`: the browser supplies command, complete encoded game state and canonical physical state. Revision locking, 100-tile inventory, immutable previously placed Stage board tiles and seeded score floor are enforced. The server does not apply or score A-Math moves. Both move score and later history remain client trusted. Live event commands are currently coarse UI labels, not sufficient for independent move replay.
4. For a finished game `commitRoomState` calls `finalize_live_game` with the browser's complete final state and completion reason. The RPC checks `status='finished'`, natural reason against the terminal log, surrender side against match control, and access. It does not check a Stage sealed start, revision, terminal transition, score, complete action sequence, or terminal canonical against the last committed position. It updates scores from browser JSON. The Stage archive policy is `none`, so it inserts no completed snapshot, then deletes `room_live`. A retry has no Stage destination to find and fails `live game not found`.
5. Separately, `App.tsx` detects a finished Stage by game **name** and calls `recordSurvivalPracticeResult`. That browser PostgREST update writes `finished_at`, both scores and `result` from its local game, with an owner/unfinished RLS guard. It can run before finalization, after deletion, or fail independently. `listMySurvivalWins` and stats read these advisory rows as wins. Authenticated users retain column UPDATE grants; an owner can directly claim a win on its own unfinished attempt without playing. The attempt row remains after room deletion.
6. The existing Compact `buildStageCompletedGameRecord` compares genesis to a supplied seal and includes seeded scores, bot and rules provenance, but is only a local adapter and labels completion `client-reported`. No production Stage completion calls it or retains its result. There is presently no completed Stage replay source. Public/Region/Private archives use the trusted `archive-replay` projection endpoint; `scope:'stage'` exists in the projection policy but has no database reader.

## Real terminal and disappearance paths

- A natural `end_game` log may report `rack_out`, `no_score_streak` or `perfect_game`. The ordinary finalizer validates that the supplied log names the supplied natural reason. It does not validate the move that produced it.
- Player end action in a versus Stage is surrender, represented by `end_game` and `matchControl.surrenderedSide`. A manual end can finish other modes. Save/Exit stop makes status `draft`, not finished; a stopped Stage can later resume. Stop is not a win.
- `cancel_live_game` and `cleanup_expired_live_games` can delete a room without a terminal capture, leaving an unfinished attempt. These are abort/expiry paths rather than completed wins. Stage finalization itself can delete the room without either an advisory result or replay.
- Repeated Stage finalization cannot make a second normal archive, because `archive_policy='none'`; currently it errors after the first deletion. Concurrent finalization serializes on the room row, but the loser also errors. Repeated direct result updates are blocked once `finished_at` is set, yet the first one can be fabricated.

## Authority ceiling for this gate

The database can establish the server-created attempt/owner/level/room, sealed start, frozen bot pin, revisioned committed state, and transactional terminal identity. It can derive a result from *the state it accepts* and refuse a separate browser boolean. It **cannot** independently prove the legality or scoring of all prior Stage moves from the current live protocol. The existing `live_game_events.command` does not contain move details, and each committed full state is client computed. A terminal record sourced from that state must say `client-reported` or equivalent, even if a trusted server stores it. A claim of fully server-authoritative final score/win would be false without a Stage move reducer or complete independent replay validator. This gap must remain explicit in the gate verdict.

## Data and disclosure

Raw completed payload must remain server only. A Stage replay should use `projectCompletedGame` with `scope:'stage'`, `published:false`, owner identity from the attempt row, and no inferred public sharing. The projection drops physical IDs, ordered bag, hidden future draws and internal bot provenance. Existing `survival_attempts` rows cannot be promoted to verified records retrospectively. Their results remain advisory. The seeded opening score is nonzero; correct reconstruction starts at the sealed `scores` and adds later log effects. Current rules provenance is `COMPLETED_RULES_VERSION` plus Stage seal version and bot config version; historic validator maintenance remains open before future rules changes.
